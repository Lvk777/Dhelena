## 1. Railway e site

- `Dhelena` e `resourceful-joy`: “Auto deploy is disabled” nos dois serviços ligados a `codex/production-hardening`. Os deployments existentes permaneceram online. `https://dhelenas.com/` e `https://api.dhelenas.com/health` responderam 200; `/health` informou `database=connected`. A raiz da API responde 404 porque as rotas funcionais ficam sob `/api`.
- `/api/settings` confirmou `maintenance_mode=true`. No backend, `MERCADO_PAGO_MODE=production`, `MELHOR_ENVIO_MODE=production`, `TRANSACTIONAL_EMAIL_ENABLED=false`, `AFTER_SALES_REFUNDS_ENABLED=false` e `SHIPPING_PREPARATION_ENABLED=true`. As flags de compra de etiqueta, worker, desconto Pix e parcelamento ampliado não estão definidas entre as variáveis de serviço e o código exige o literal `true` para ativá-las. A Data API do Supabase mostra “Data API is disabled”.
- Defeito reproduzido: `/assets/<arquivo-ausente>.js` na versão publicada responde 200 `text/html`; o Cloudflare retornou `Cache-Control: max-age=14400` e depois `CF-Cache-Status: HIT`. Isso pode servir HTML onde o navegador exige JS e manter tela branca.
- Correção **somente local**: `static-server.mjs` serve arquivo existente, retorna 404/no-store para assets ausentes, usa no-store para HTML e cache imutável para assets com hash; o roteamento SPA mantém fallback apenas para navegação. `npm start` usa esse servidor; `railpack.json` fixa o provedor Node e o comando de start para não depender da detecção automática de SPA. Teste e smoke HTTP locais passaram. A próxima implantação exige autorização separada, confirmação do comando de start no Railway e verificação/purge dirigido das respostas HTML antigas em `/assets` no Cloudflare. Não presumir que o código sozinho remove objetos já cacheados no edge.
